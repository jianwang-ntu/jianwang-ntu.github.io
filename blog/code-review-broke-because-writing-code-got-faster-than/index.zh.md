# 当写代码比读代码快：一篇中文博文为「代码审查已死」做的辩护与修正

![Code Review Broke Because Writing Code Got Faster Than Reading It](https://publicsg.s3.ap-southeast-1.amazonaws.com/github.io/images/blog/code-review-broke-because-writing-code-got-faster-than.png)

一篇发表在 lightnote 的中文长文提出，从 Fagan 在 1976 年正式提出代码检查算起，「让另一位人类在合并前读一遍」这条延续了五十年的基石实践，正在 2026 年失效。作者的论据不是 AI 更聪明了，而是一个更朴素的理由：代码审查一直依赖「读比写快」这个偶然的速度差，而这个前提已经不成立。

## 崩塌的前提：读代码不再便宜

文章把传统审查的有效性归因于一个「速度的错位」：资深工程师看代码的速度远快于新手写代码的速度，于是审查天然跟得上节奏，团队顺便通过读 diff 吸收架构、完成隐性知识转移。作者认为这一切都建立在「写代码又慢又贵，读代码既便宜又快」之上。

如今 Claude Code、Codex、GitHub Copilot 这类编码代理能在几秒内产出上千行格式整齐的代码，而人类阅读速度几十年原地踏步。文章因此断言，软件工程中最难的部分已经换了位置：

> 「已经从『怎么写出这段代码』变成了『我到底该不该信任这段代码』。」

## 作者引用的数据

文章援引 Faros AI 在 2026 年第一季度对 4,000 个团队、22,000 名开发者的追踪，列出采用 AI 后的五项变化：代码变动率（code churn）上升 861%，审查耗时中位数上涨 441.5%，开发者缺陷率从 9% 升到 54%，事故与 PR 的比例上升 242.7%，零审查直接合并的 PR 增加 31.3%。

作者最在意的是最后一项，并给出了自己的解读：31.3% 不是团队集体决定不审查，而是「根本看不过来」——当代码量超过流程的吸收能力，闭眼点 Merge 就成了默认行为。文章还引用 GitClear 创始人 Bill Harding 的测算：AI 用户每天产出的原始代码量是不用 AI 者的 4 倍，但交付的实际价值只增加约 12%。四倍的代码，一成出头的价值，而人类仍然要逐行看完这四倍。作者认为这就是当前审查危机的核心。

## 两份文献，两种结论

文章的分析架在两份材料上，并且刻意让它们互相拉扯。

一边是 KTH 皇家理工学院 Martin Monperrus 的论文《The End of Code Review: Coding Agents Supersede Human Inspection》。据文章转述，Monperrus 的立场相当激进：代理能力已越过红线，人工审查完全多余，该让机器查机器。理由包括 SWE-bench 上最先进代理端到端解决率超过 80%、代理生成的内联缺陷注释质量已可与受训人类审查者相当，以及代理能覆盖人类关注的全部缺陷类型。作者特别指出，该论文直言「AI 写、人类强制审查」的中间模式是死胡同——既不保证质量，也扛不住吞吐量。

另一边是 Google 资深工程师 Addy Osmani 的《Agentic Code Review》。文章认为 Osmani 点到了论文没覆盖的痛处：AI 代码难审查，是因为**意图和推理过程丢失了**。人类写代码时意图是自带的，权衡过和放弃过的方案都会在 review 时讨论；现代代理虽然会生成 thinking traces，但这些推理在生成 diff 的那一刻就被丢弃。审查者只能对着冷冰冰的代码逆向推导意图。作者把这一点直接指认为审查耗时暴涨 441% 的元凶。

## 三种场景，三套策略

文章反对在「AI 代码根本不用看」和「每一行都要两人逐字审」之间站队，主张策略应跟着三个变量走：爆炸半径、代码寿命、团队规模。

- **单人原型**：知识共享这一审查目的本身不成立，可以把把关交给自动化测试；但作者提醒，不审查不等于不验证——测试覆盖率薄的时候跳过审查是在挖坑。
- **成长型团队**：文章称这是最容易翻车的中间地带，建议分层审查——静态分析和安全扫描交给 CI/CD，CodeRabbit 或 Claude Code 做初步逻辑审查，人只盯核心业务逻辑、架构影响和知识传递。作者的说法是：别让人去抠 AI 写的循环效率，让他们去想这个循环该不该存在。
- **企业级重型系统**：主张证据驱动的审查，拒收只有代码的 AI PR，要求代理交出决策日志。文章借 Osmani 的话收尾：你的工作不是写代码，而是交付你已经证明有效的代码。

## 作者给出的三招

对应上面的诊断，文章提出三条可操作的做法：一是在 prompt 和团队规范里强制 AI 产出 `DECISION_LOG.md`，附上推理轨迹和被否决的备选方案，作者称这能省下大部分逆向工程时间；二是「用 AI 审查 AI」，在 CI 里放一个审查代理，在人看到 PR 之前先跑一轮，并给它具体规则（例如检查是否引入了 `architecture.md` 明令禁止的循环依赖），以拦截那些「看着像模像样其实全是废话」的产物；三是把审查从「这段代码写得对不对」改问成「它解决的问题对不对、有没有把系统带偏」。

## 值得留意的一点

需要说明的是，文章引用的两份文献均标注为 2026 年，其中 Monperrus 论文给出的是 arXiv 预印本编号；文中的所有数据、论断和结论都出自该文对这两份材料及 Faros AI、GitClear 数据的转述，读者若要采信，最好回到原始来源核对。

作者本人的落点则很清楚：代码审查的终结不意味着没人管质量，而是程序员角色的重新洗牌。写代码的成本被打到地板价，但「搞懂这个系统」的成本依然高昂。按文章的说法，未来几年最强的团队不是产出代码最多的那个，而是建起了一套他们真正敢闭眼信任的审查系统的团队——并且永远不会把「绿灯全亮」和「有人真的懂这堆代码在干嘛」混为一谈。
