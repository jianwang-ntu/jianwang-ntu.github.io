Research statement · 28 October 2026

Learning Reusable Reasoning for Reliable AI-Assisted Programming

Scope
Learning and evaluating reasoning for software understanding, generation, repair, and maintenance.
Aim
Develop transferable programming strategies and agents whose software changes and completion claims can be independently assessed.

I study how AI systems learn reasoning strategies that transfer across programming tasks, and how coding agents use those strategies to make dependable software changes. My goal is to improve both an agent’s ability to solve a task and the basis for judging whether its solution satisfies the intended requirements.

This agenda connects learning reusable reasoning for programming with building reliable coding agents. The first direction asks what models learn from experience; the second asks how agents use that learning across a sequence of software changes. I would assess reliability against explicit functional and security requirements, using execution, testing, static analysis, and formal verification where applicable. Each provides evidence with a defined scope; none substitutes for specifying the intended behavior.

Two connected directions
  1. Learning reusable reasoning for programming
  2. Building reliable coding agents

Research direction 1

Learning reusable reasoning for programming

How can models learn reasoning strategies that transfer across programs and tasks?

I use reusable reasoning to mean strategies for selecting subproblems, forming and revising hypotheses, and choosing checks that remain useful on unfamiliar code. For example, an agent might construct an input that distinguishes two explanations of a failure, or introduce an invariant that connects a loop’s behavior to a required property.

I would investigate learning from records that connect a programming decision to the code state, tool action, and observed result. The hypothesis is that this supervision can improve transfer beyond training on successful final solutions alone. Comparing alternative actions from the same program state would help test which decisions contribute to improvement. Explanations would be assessed against observable behavior and checked artifacts; fluent rationales alone would not count as evidence of reasoning quality.

Evaluation would separate gains from training, retrieval, and additional search at inference. Comparisons would use the same starting model, accessible tools, and test-time budget, while reporting training and data-collection costs. Tests on held-out repositories and program families, with near-duplicate controls, would measure solution correctness, adaptation to changed requirements, and the cost of reaching a supported solution. Loop-invariant synthesis and revision would provide an initial setting, with transfer tested in debugging, repair, and program understanding.

Research direction 2

Building reliable coding agents

How can agents make useful software changes while preserving required behavior?

A software change can fix a reported failure while breaking behavior elsewhere. Earlier evidence may also cease to apply when code, dependencies, or assumptions change. The research question is how an agent should decide what to inspect, what to recheck, and when the available evidence is insufficient to claim completion.

I would investigate agents that maintain explicit links between requirements, code versions, changes, and check results. These links would identify evidence affected by an edit and guide targeted rechecking, further investigation, or human review. Requirements and evaluation checks used to judge success would remain outside the agent’s authority to weaken. The hypothesis is that managing these dependencies can reduce missed regressions and unsupported completion claims at a practical cost.

Experiments would compare this approach with ordinary iterative repair and approaches that rerun all available checks, under matched tool access and budgets. Repository-level repair and maintenance tasks would include changes across interacting components. Independent tests, targeted security checks, and formal specifications where available would assess requirement satisfaction separately from success on agent-visible checks. Evaluation would measure completed tasks, regressions, unsupported completion claims, checking cost, and human review effort. Guarantees would be limited to the properties, models, assumptions, and trusted tools actually used.

The intended contribution is an account of which programming strategies transfer, together with methods for keeping the evidence behind an agent’s software changes current and open to independent assessment.

Research foundation

My work in code-model evaluation, program repair, and loop-invariant synthesis provides the foundation. Related projects include Loop-R1, Defects4C, RATCHET, and execution-trace evaluation. The learning and agent methods described above are proposed research.

Related verification work provides concrete context: Anthropic and Theorem describe proofs of specified software properties under explicit execution assumptions; Theorem’s verified-stack proposal emphasizes reuse through verified component interfaces; and the Verus guide motivates protecting specifications and checking for invalid proof shortcuts.
