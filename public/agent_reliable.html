Research statement · 29 October 2026

Learning Reusable Reasoning for Reliable AI-Assisted Programming

Scope
AI-assisted software development in unfamiliar codebases and increasingly complex workflows.
Aim
Learn how to adapt reasoning to a new environment, then sustain reliability as the work expands.

I study how AI coding agents become useful in unfamiliar software environments and remain reliable as their work expands. Consider an agent asked to fix a crash in a library it has never seen: it must understand the relevant behavior, investigate the cause, and determine what would count as a valid repair.

My agenda follows this progression. Learning reusable reasoning asks how experience with earlier problems can help the agent investigate a new codebase. As its work extends to callers, dependencies, and sequences of changes, building reliable coding agents asks how those reasoning capabilities can support a coherent workflow. The first direction concerns adaptation to unfamiliar problems; the second concerns reliability as the scope and duration of work grow.

Informal reasoning helps the agent interpret a bug report, infer intent from documentation, and form explanations from code and observed executions. In the crash example, it might suspect an off-by-one error and design a test to distinguish that explanation from a missing input check. Tests and traces provide concrete evidence about executed cases, but do not by themselves establish a property for every possible execution.

Formal reasoning begins with a precise requirement and an explicit model of how the program executes. For the same repair, a developer-reviewed specification might require every array access to remain within bounds; a verification tool derives the logical conditions needed for that property, and checked proofs establish it under the stated assumptions. Workflows such as Verus proof development provide this kind of feedback. The two forms of reasoning can occur within one task: informal investigation suggests what to check, while formal checking assesses a precisely stated claim. A failed proof attempt can leave that claim unresolved, and a successful proof still requires human judgment about whether the specification captures the intended requirement.

Two connected directions
  1. Learning reusable reasoning for programming
  2. Building reliable coding agents

Research direction 1

Learning reusable reasoning for programming

How can experience solving earlier problems help an agent reason in a new software environment?

Reasoning is useful here because the agent must decide which parts of an unfamiliar program matter, which explanation fits the failure, and what evidence would change its next action. My existing work provides a starting point for studying how these decisions can be learned. The Loop-R1 preprint reports improved invariant synthesis after reasoning-oriented fine-tuning in its evaluated settings, with limited performance on more complex programs. Our execution-trace study found limited gains from adding trace information in its tested training and inference settings. Together, these findings motivate studying how feedback is used, rather than assuming that supplying more information will improve reasoning.

This foundation motivates a testable hypothesis: learning which decisions are supported or contradicted by feedback can improve adaptation to unfamiliar programs, compared with learning only from final solutions. For the crash example, a training record could connect a proposed cause to a diagnostic input and its observed result, showing when that explanation should be revised. A proof-oriented record could connect a proposed loop invariant—a property intended to hold throughout a loop—to the logical condition it fails to establish, while distinguishing a rejected proof attempt from a demonstrated program defect. Here, reusable means a strategy for choosing and interpreting such checks that remains useful on new code. The prior work establishes useful starting tasks and feedback sources; it does not establish this transfer hypothesis.

I would begin with invariant revision, where candidate claims can be checked precisely, then test transfer to debugging and repair. Comparisons would match training tasks, model starting points, tool access, and resource budgets, while reporting data-collection costs. Held-out repositories and program families would control near-duplicates and retrieval overlap. Evidence for transfer would require higher independently assessed correctness at matched cost, or lower cost at matched correctness, with separate comparisons for retrieval and additional inference-time search.

Research direction 2

Building reliable coding agents

How can reliability persist as an agent’s work grows across components, dependencies, and time?

After the agent repairs the library function, its work may expand to updating callers, accommodating a dependency change, or maintaining the system through later revisions. The reasoning strategies studied in the first direction help it address each unfamiliar problem, but a sequence of locally successful changes may still violate a broader requirement. The second direction therefore studies how individual decisions can support reliable behavior at the scale of a software workflow.

I would investigate how agents preserve objectives, manage uncertainty, and recover from mistakes as tasks become longer and more interconnected. The central questions concern when earlier conclusions remain applicable, how interacting changes affect one another, and when the evidence warrants continuing, revising a plan, or seeking human judgment. The aim is sustained progress that respects the task’s functional and security requirements.

Evaluation would increase task duration and component interaction while comparing agents under matched tool access and budgets. Independent checks would assess completion, regressions, recovery, and review effort separately from success on agent-visible checks. Requirements would remain fixed for each comparison. The question is whether reliability can be sustained as useful work expands, at an explicit cost. Formal guarantees would cover only the specified properties under the models, assumptions, and trusted tools actually used.

My long-term goal is AI systems that learn to solve unfamiliar programming problems and produce software people can depend on. The two directions form a continuing loop: transferable strategies help agents enter new environments, reliable workflows govern their use as work expands, and workflow failures expose what those strategies still need to learn.

Research foundation

My work in code-model evaluation, program repair, and loop-invariant synthesis provides the foundation. Related projects include Loop-R1, Defects4C, RATCHET, and execution-trace evaluation. The learning and agent methods described above are proposed research.

Related verification work provides concrete context: Anthropic and Theorem describe proofs of specified software properties under explicit execution assumptions; Theorem’s verified-stack proposal emphasizes reuse through verified component interfaces; and the Verus guide motivates protecting specifications and checking for invalid proof shortcuts.
